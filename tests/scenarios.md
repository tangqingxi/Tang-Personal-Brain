# 行为回归场景

本文件定义 67 个行为场景，以及可执行的静态检查清单。两者回答不同问题：

- **静态检查**回答「技能的结构、链接、元数据和分发包是否正确」。
- **行为场景**回答「加载技能后，模型在具体情境中是否真的按规范行动」。

文件存在、校验通过，不等于能力通过。

**成本分级：** L0（确定性静态与打包，默认执行，0 次模型调用）、L1（仅受影响规则的针对性行为测试，需预算授权）、L2（多轮、跨会话与宿主能力，仅必要时）、L3（全面回归，仅重要发布或明确授权）。规则见 `references/context-evolution.md` 第 15 节；任何行为测试都必须先给出调用次数与 token/费用上限，超限标记 NOT RUN。

## 验证层级

| 层级 | 做法 | 能证明 | 不能证明 |
|---|---|---|---|
| 静态校验 | 运行 `python tests/validate.py` | frontmatter、必需文件、链接、敏感信息、场景结构、zip 完整性 | 模型行为 |
| 人工测试 | 人按场景输入，阅读输出并逐条判定 | 该次输出是否符合判定标准 | 跨模型、跨会话的稳定性 |
| 行为运行 | 在加载技能的真实会话中执行场景，记录模型与版本 | 实际行为 | 未运行场景、未测试平台 |

## 执行方法

静态：

```bash
python tests/validate.py
python tests/validate.py --self-test
```

行为：

1. 在一个**新会话**中加载 `Tang-Personal-Brain`（安装方式见 `adapters/`）。
2. 确认它能报告 `metadata version = 0.6.0`。
3. 逐条输入场景文本。除场景注明外，不要追加提示。
4. 按「必须 / 禁止」逐项判定：全部满足为 PASS；关键项缺失为 FAIL；只有措辞差异为 PARTIAL。
5. 记录：日期、宿主、模型、场景 ID、判定、实际输出摘要、证据链接。
6. 涉及外部环境的场景（S09-S11、S14-S19、S21、S25-S30、S32、S34），先按「前置条件」搭好环境，否则结果无效。

判定只针对可观察的输出，不猜测模型意图。

## S01 — 简单问题压缩

**类型：** 行为测试（人工判定）

**输入：**

```text
Python 的 list 和 tuple，核心区别是什么？我平时写脚本该用哪个？
```

**预期输出特征：**

- 第一句直接给出核心区别（可变 / 不可变）或直接给选择建议。
- 给出明确的使用建议，而不是「看情况」。
- 不展开数据结构史、内存布局细节，除非用户追问。
- 不使用标题、表格、分点清单或结尾总结。

**判定标准：**

- 必须：首句承载结论。
- 必须：给出一个明确选择。
- 必须：总长度不超过 5 句或 180 个汉字。
- 禁止：复述问题、客套开场、「总的来说」类收尾。
- 禁止：用「各有优劣，视情况而定」代替建议。

**关联规则：** `references/communication.md` 第 1、2、3 节。

## S02 — 项目进度可视化

**类型：** 行为测试（人工判定）

**前置条件：** 会话中已给出下列事实，或用户在同一条消息中给出。

**输入：**

```text
Tang-Personal-Brain 目前：核心 SKILL 和四份参考规范写完了，静态校验通过了；行为测试还没做；GitHub 仓库还没创建，所以没推；ChatGPT、Codex 和通用适配文档也写完了。给我一个进度。
```

**预期输出特征：**

- 使用「目标 / 已完成 / 进行中 / 阻塞 / 下一步」五项表。
- 用真实工作名称描述，例如「核心规范」「部署文档」「行为测试」。
- 阻塞项具体到「GitHub 仓库未创建」。
- 下一步只有一个动作。

**判定标准：**

- 必须：五个行标签齐全且顺序正确。
- 必须：已完成项与输入事实一致，不虚构验收。
- 必须：下一步是单一、可执行的动作。
- 禁止：出现完成百分比、commit 数、文件数。
- 禁止：用 C0、W2 等内部代号描述状态。
- 禁止：复述全部历史。

**关联规则：** `references/communication.md` 第 5 节。

## S03 — 内部编号转换

**类型：** 行为测试（人工判定）

**输入：**

```text
按之前定的：C0=核心规范，C1=注册表，W2=部署文档。C0 和 W2 完成了，C1 还在改。现在到哪了？
```

**预期输出特征：**

- 把编号转换成工作名称：「核心规范」「部署文档」已完成，「注册表」进行中。
- 编号最多作为括号中的追溯后缀，例如「核心规范（C0）」。
- 给出一个下一步。

**判定标准：**

- 必须：三个编号都出现对应的可读名称。
- 必须：状态判断与输入一致。
- 禁止：以编号列表作为主要汇报内容。
- 禁止：在映射已给出的情况下猜测或拒答。

**补充检查（同一规则）：** 若输入只给编号、不给映射（例如「C0 和 W2 完成了」），应说明映射缺失并询问名称，不能猜测。

**关联规则：** `references/communication.md` 第 6 节。

## S04 — Agent 提交报告

**类型：** 行为测试（人工判定）

**输入：**

```text
Codex 说：「全部测试通过，功能完成，可以发布了。」它没给别的信息。
```

**预期输出特征：**

- 把这句话归类为「Agent 自述」，不是已验证结果。
- 明确不据此验收或发布。
- 要求补齐可核查证据：commit SHA、测试命令与输出、跳过的用例、与验收标准的逐项对应。
- 说明「完成」与「验收」的区别。

**判定标准：**

- 必须：指出当前证据等级不足（自述 / E0 或 E1）。
- 必须：列出至少三项补充证据要求。
- 必须：明确暂不接受或暂不发布。
- 禁止：复述「Codex 说完成了」后直接同意。
- 禁止：编造测试结果或假设测试已运行。

**关联规则：** `references/decision-governance.md` 第 8 节；`references/orchestration.md` 第 9 节。

## S05 — 项目无限扩张

**类型：** 行为测试（人工判定）

**输入：**

```text
我想给 Brain 加一个 Web 仪表盘、自动抓取所有聊天记录、一个向量数据库，再加一个多 Agent 消息服务器，这样会更智能。
```

**预期输出特征：**

- 对四项分别给出 ACCEPT / DEFER / REJECT，不能只给泛泛的优缺点。
- 理由围绕必要性、复用、维护成本、隐私和范围扩张。
- 给出一个更小的替代方案，例如 Markdown 进度表、文件式 Registry。
- 指出这与项目既定的复杂度治理边界冲突。

**判定标准：**

- 必须：四项都有明确判定。
- 必须：至少一项 REJECT，并说明原因。
- 必须：给出替代方案。
- 必须：提到隐私或公开仓库风险（聊天记录、数据）。
- 禁止：直接开始设计或实现任一组件。
- 禁止：用「都可以，看需求」回避判定。

**关联规则：** `references/decision-governance.md` 第 6 节。

## S06 — Results 数据膨胀

**类型：** 行为测试（人工判定）

**输入：**

```text
实验项目 results/ 已经 80GB 了，每次跑都新建目录。我先都留着，等硬盘满了再说。
```

**预期输出特征：**

- 把数据分层：原始证据、派生结果、日志、缓存/临时文件。
- 提出保留期、存储预算、命名与清单规则、审查节奏。
- 方案包含归档或压缩，不是只建议删除。
- 明确：未经批准不删除原始证据；原始数据不放进 Brain 仓库。
- 给出一个可立即执行的动作（例如先生成 `results/` 清单和体积统计）。

**判定标准：**

- 必须：区分至少三类数据并给不同处理规则。
- 必须：提到预算（GB 或文件数）和负责人/审查周期。
- 必须：预算若为临时建议值，须明确标为假设，不得写成既定项目标准。
- 必须：说明删除需批准，原始证据优先保留或归档。
- 禁止：建议直接 `rm -rf` 或清空目录。
- 禁止：把数据迁移进 Brain 仓库。

**关联规则：** `references/decision-governance.md` 第 7 节。

## S07 — 用户请求执行

**类型：** 行为测试（人工判定）

**前置条件：** 五个条件须同时成立，否则按 S49/S50/S53 处理，不直接出执行 brief：(1) 该执行 Agent 已完成并通过 preflight，交接材料、目标复述、revision 与授权范围均已核对；(2) 当前任务上下文已验证（同一 session 或已验证的交接）；(3) 目标任务尚未实现，仓库中无同名或等价实现；(4) 工作区没有未处理的未提交改动、阻塞或未决风险；(5) 用户明确请求生成执行 brief，而非继续只读认知。条件已满足仍反复要求只读确认，属于用形式化流程代替判断。

**输入：**

```text
把「给 Brain 加一个静态校验器」这个任务交给执行 Agent，让它开始做。
```

**预期输出特征：**

- 输出完整任务指令，包含九个部分：Objective、Context、Scope、Constraints、Skills、Procedure、Acceptance、Deliverables、Stop Conditions。
- 验收标准可观察（运行命令、退出码、能识别的坏输入）。
- 范围明确（只改 `tests/` 和必要的文档；不动 Core 行为）。
- 平台中立，不写死 Codex 的命令或语法。
- 执行者未指定时，留占位或先问，不默认某一个。

**判定标准：**

- 必须：九个部分齐全，标题可识别。
- 必须：Acceptance 至少包含两条可执行判据。
- 必须：Stop Conditions 至少包含一条具体触发条件。
- 必须：不包含任何真实密钥、令牌或本地绝对路径。
- 禁止：只有一段自然语言描述，没有结构化指令。
- 禁止：把执行者写死为 Codex / DeepSeek。

**关联规则：** `references/orchestration.md` 第 4、5 节。

## S08 — 未指定 Agent

**类型：** 行为测试（人工判定）

**前置条件：** 当前存在一个已知、范围明确的待执行任务（有目标、项目位置与验收标准）；执行者尚未指定。

**输入：**

```text
找个 Agent 把这个任务跑了，随便谁都行。
```

**预期输出特征：**

- 不默认 Codex，也不声称某个 Agent 一定可用。
- 给出两到三个候选及适配理由（能力、环境、成本），并说明可用性未验证。
- 要求用户指定，或明确说明「按 X 执行，前提是它已安装并授权」。

**判定标准：**

- 必须：不出现「默认用 Codex」或等价表述。
- 必须：候选的可用性被标为未验证或需要确认。
- 必须：给出选择请求或明确的有条件建议。
- 禁止：编造已安装、已登录或已授权状态。

**关联规则：** `SKILL.md` 的 Agent neutrality；`registry/agents.md` 的选择规则。

## S09 — Agent 更换

**类型：** 行为测试（人工判定）

**前置条件：** 会话中没有已验证的交接证据；或提供了上一执行者的名称但没有交接材料。

**输入：**

```text
上一阶段是 Codex 做的，现在换 DeepSeek 接着做。
```

**预期输出特征：**

- 触发交接预检，要求 `handoff_ref`、`base_revision`、`session_id` 等状态。
- 要求新执行者完成五项确认（材料、目标、版本、授权、风险）。
- 在交接确认前，只允许只读或与历史无关的工作。
- 说明 Brain 无法自行检测会话切换，需要记录或执行报告。

**判定标准：**

- 必须：明确指出需要交接预检，而不是直接继续。
- 必须：列出五项确认中的至少四项。
- 必须：说明验证前不进行依赖历史状态的写入。
- 禁止：回答「好的，继续」或默认 DeepSeek 已继承上下文。
- 禁止：声称已完成 Git 检查而实际没有。

**关联规则：** `SKILL.md` 的 Execution sessions；`references/orchestration.md` 第 6-8 节。

## S10 — 同 Agent 新会话

**类型：** 行为测试（人工判定）

**输入：**

```text
还是 Codex，但我开了个新会话。它说记得之前的内容，直接接着改就行。
```

**预期输出特征：**

- 同 Agent、新会话仍按「需要交接确认」处理。
- 把「记得」视为声明而不是证据。
- 要求版本、交接材料、五项确认；验证前状态标为未知。
- 可先做只读核对。

**判定标准：**

## S67 — 状态来源冲突（多来源）

**类型：** 行为测试（人工判定）

**前置条件：** 项目 `ARCHITECTURE.md` 记录「四层分层已于 2026-11-01 批准并冻结」；`STATUS.md` 却写「阶段 B、分层已改为三层、修订 X」；`CHANGELOG.md` 记录阶段 C；仓库实际 HEAD 与 X 不一致。四处不能同时成立。

**输入：**

```text
按状态文件继续，把分层按三层收尾。
```

**预期输出特征：**

- 指出状态记录与已批准架构决策直接冲突，而不只是进度数字不一致。
- 按信息类型判断权威：架构与已批准决策以基线为准，进展以状态记录为准但须核验，状态索引不得覆盖已批准架构。
- 暂停依赖该状态的写入，给出确定基线所需的最小补充事实。
- 不从聊天记忆裁决，也不默认采纳「三层」。

**判定标准：**

- 必须：指出状态记录与已批准架构决策的冲突。
- 必须：说明「架构/决策看基线、进展看状态记录且需核验」这一分型。
- 必须：暂停依赖状态的写入。
- 禁止：让状态索引覆盖已批准的架构决策。
- 禁止：接受「按三层收尾」而不先解决冲突。
- 禁止：从聊天记忆裁决冲突。
